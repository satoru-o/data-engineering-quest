# 02. パイプラインの形 — 境界をどこに引くか

パイプラインを書く前に決めておくとよいことが2つあります。**層をどう分けるか**と、
**1回の実行がどの範囲を担当するか**です。

この2つを決めないまま書き始めると、処理が1つの大きなスクリプトにまとまってしまい、
あとから一部だけ流し直すのが難しくなります。

## 層を分ける

取り込みから提供までを一息に書かず、**途中の状態をファイルやテーブルとして残しておきます。**

呼び名は2系統ありますが、中身は同じものです。

| メダリオン | 従来型 | 中身 | 変えてよいか |
| --- | --- | --- | --- |
| **Bronze** | raw / landing | 生データそのまま。無加工 | **変えない** |
| **Silver** | staging / cleansed | 型・表記・粒度を揃えたもの | 仕様変更で作り直す |
| **Gold** | marts / serving | 業務の意味で集計したもの | 用途ごとに何個でも |

### なぜ中間を残すのか

**やり直せる単位を作るためです。**

```
生 → [変換] → 提供            変換のバグに気づいたとき、上流から取り直すことになる
生 → 整形 → 集計 → 提供        集計を直して流し直すだけで済む
```

上流が外部APIで、過去の分をもう取得できない場合、
中間を残していないと、そのデータは戻せなくなります。

### Bronzeを変えない、の意味

Bronze は「読めなくてもよい」層です。文字化けしていても、列がずれていても、
**届いたバイト列をそのまま置きます**。

- 圧縮はしてかまいません(可逆なら)
- 取り込み時刻とソースファイル名のメタデータは足してかまいません
- **値そのものはいじりません**

「どうせ整形するのに、なぜ汚いまま置くのか」と思うかもしれません。
理由は、**整形のロジックが間違っていたと後から分かることがある**ためです。
そのとき手元に元データがあれば、やり直せます。

## 1回の実行が担当する範囲

ここが設計の中心です。パイプラインの1回の実行を、何で区切るかという話です。

### 素朴な形: 全件洗い替え

```
毎回:  ソースを全部読む → 出力を全部消す → 全部書く
```

| 良い点 | 気をつける点 |
| --- | --- |
| 単純。冪等になる | データ量に比例して遅くなる |
| 過去の修正が自動で反映される | いずれ実行時間が窓に収まらなくなる |
| | 実行中、出力が空になる瞬間がある |

**データが小さいうちは、これで十分です。** 数GBくらいまでなら全件洗い替えで足ります。

むしろ、早い段階で増分処理にすると、条件の詰めが甘いまま
ウォーターマーク(どこまで処理したかの目印)を埋め込んでしまいがちです。
**素朴な形から始めて、遅くなってきたら次の形に移る**、という順番が安全です。

### 育った形: 期間で区切る

```
1回の実行 = 1つの期間ぶん   (2024-01-15 の1日ぶん、など)
```

この単位を**パーティション**と呼びます。実行するときは「どの期間か」を引数で渡します。

```bash
python pipeline.py --date 2024-01-15
```

ここで一点だけ、**今日の日付をコードの中で取らない**ようにしておくと後が楽です。

```python
target = datetime.date.today()      # 過去分を流し直せなくなる
target = args.date                  # 外から渡す
```

`today()` が処理の中に入っていると、過去の日付で実行し直すこと(バックフィル)ができません。
あとから直すのは手間がかかるので、最初から外から渡す形にしておきます。

### 書き込みも期間で区切る

出力側も同じ単位で分けておくと、**その期間だけを差し替えられます**。

```
out/orders/date=2024-01-14/part-0.parquet
out/orders/date=2024-01-15/part-0.parquet    ← ここだけ消して書き直せる
out/orders/date=2024-01-16/part-0.parquet
```

これがパーティショニングで、
「1つのディレクトリ = 1つの差し替え単位」という形になります。
読む側も `WHERE date = '2024-01-15'` でディレクトリごと読み飛ばせます([05](05-columnar-and-parquet.md))。

## どの時刻で区切るか

「1日ぶん」の1日を、**どの列で切るか**という話です。ここは数字が合うかどうかに直結します。

| 時刻 | 意味 | 特徴 |
| --- | --- | --- |
| **イベント時刻** | 実際に注文が起きた時刻 | 業務的に正しい。**遅れて届くことがある** |
| **取り込み時刻** | こちらに届いた時刻 | 遅れない。ただし業務の意味とはずれる |

```
1/15 23:58 に注文  →  ネットワーク遅延  →  1/16 00:03 に届く

イベント時刻で切る:  1/15 のパーティションに入る。ただし 1/15 のバッチは終わっている
取り込み時刻で切る:  1/16 のパーティションに入る。1/15 の売上が 1/16 に計上される
```

**どちらにも一長一短があります。** よく使われるのは次の組み合わせです。

- **保存はイベント時刻で区切る**(業務的な正しさを優先する)
- **遅れて届いた分で、過去のパーティションを作り直す**(バックフィル)
- **いつまで遅れを待つかを決めておく**(ウォーターマーク → [04](04-idempotency-and-replay.md))

「1/15のデータは1/16の朝には確定している」ではなく、
「**1/15のデータは1/18くらいまで変わりうる**」という前提で組んでおくと、あとで慌てずに済みます。

## タイムゾーン

日次バッチの「1日」は、誰にとっての1日でしょうか。

- 保存は **UTC** に統一します
- 区切りと表示のときだけ **JST** に変換します
- 列名に単位を書いておきます。`created_at_utc` / `order_date_jst`

タイムゾーンが混ざった列は、あとから分けるのが難しくなります。
`2024-01-15 09:00` という値を見ても、UTC なのか JST なのか判断できないためです。

これは [03](03-dirty-data.md) でいう「意味の汚れ」にあたり、
見た目には異常が無いので、気づくまでに時間がかかりやすい種類です。

## 依存とオーケストレーション

層を分けると、実行順の依存が生まれます。

```
     取り込み(注文)  ──┐
                      ├─→  整形  ──→  集計  ──→  BI
     取り込み(顧客)  ──┘
```

これを回すのがオーケストレータ(Airflow / Dagster / Prefect)の役割です。
中心にある考え方は DAG(有向非巡回グラフ)で、
**「何を、何のあとに、どの単位で」** を宣言します。

`cron` で時刻をずらして並べる方法もありますが、これは依存関係を
「たぶん終わっているだろう」という想定で表している状態になります。
上流が5分遅れた日には、下流が**古いデータのまま成功してしまいます**。

| | cronで時刻をずらす | DAGで依存を書く |
| --- | --- | --- |
| 上流が遅れたら | 下流が古いデータで**成功する** | 下流が待つ |
| 上流が失敗したら | 下流が**走ってしまう** | 下流が走らない |
| 過去分の再実行 | 手で順番に叩く | 期間を指定して一括 |

詳しくは [07](07-orchestration.md) で扱います。

## 設計の順番

1. **層を決める**(生 / 整形 / 集計)
2. **区切りを決める**(日次か時次か。どの時刻列で切るか)
3. **1回の実行を、期間を引数に取る関数として書く**
4. **その期間の出力を、丸ごと差し替えられるようにする**
5. **依存を DAG で宣言する**

3 と 4 ができていれば、たいていの障害は「その期間だけ流し直す」で復旧できます。
まずはこの2つを目指すとよいです。
