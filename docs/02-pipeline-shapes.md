# 02. パイプラインの形 — 境界をどこに引くか

パイプラインを書く前に決めることが2つある。**層をどう分けるか**と、
**1回の実行がどの範囲を担当するか**。

この2つを決めずに書き始めたパイプラインは、必ず一枚岩の巨大なスクリプトになり、
一部だけ流し直すことができなくなる。

## 層を分ける

取り込みから提供までを一息で書かない。**中間状態を必ず永続化する。**

よく使われる呼び名は2系統ある。中身は同じ。

| メダリオン | 従来型 | 中身 | 変えてよいか |
| --- | --- | --- | --- |
| **Bronze** | raw / landing | 生データそのまま。無加工 | **絶対に変えない** |
| **Silver** | staging / cleansed | 型・表記・粒度を揃えたもの | 仕様変更で作り直す |
| **Gold** | marts / serving | 業務の意味で集計したもの | 用途ごとに何個でも |

### なぜ中間を残すのか

**やり直せる単位を作るため。** これに尽きる。

```
生 → [変換] → 提供            変換のバグに気づいたとき、上流から取り直すしかない
生 → 整形 → 集計 → 提供        集計を直して流し直すだけで済む
```

上流が外部APIで、過去分をもう取得できない場合、
中間を残していなければ**データが永久に失われる**。

### Bronzeを変えない、の意味

Bronzeは「読めなくてもいい」層。文字化けしていても、列がずれていても、
**届いたバイト列をそのまま置く**。

- 圧縮はしてよい(可逆なら)
- 取り込み時刻とソースファイル名のメタデータは足してよい
- **値は一切いじらない**

「どうせ整形するのに、なぜ汚いまま置くのか」への答えは、
**整形のロジックが間違っていたことが後で判明するから**。

## 1回の実行が担当する範囲

ここが設計の本丸。パイプラインの1回の実行を、何で区切るか。

### 悪い形: 全件洗い替え

```
毎回:  ソースを全部読む → 出力を全部消す → 全部書く
```

| 良い点 | 悪い点 |
| --- | --- |
| 単純。冪等 | データ量に比例して遅くなる |
| 過去の修正が自動で反映される | いずれ実行時間が窓に収まらなくなる |
| | 実行中、出力が空になる瞬間がある |

**小さいうちは正しい選択。** データが数GBまでなら、これで全部済む。
早すぎる増分化は、ほぼ確実に間違ったウォーターマークを埋め込む。

### 良い形: 期間で区切る

```
1回の実行 = 1つの期間ぶん   (2024-01-15 の1日ぶん、など)
```

この単位を**パーティション**と呼ぶ。実行は必ず「どの期間か」を引数に取る。

```bash
python pipeline.py --date 2024-01-15
```

**今日の日付をコードの中で取ってはいけない。**

```python
target = datetime.date.today()      # NG。過去分を流し直せない
target = args.date                  # OK
```

`today()` が埋め込まれた瞬間、バックフィル(過去分の再実行)が不可能になる。
これは後から直すのが非常に面倒なので、最初から外から渡す。

### 書き込みも期間で区切る

出力側も同じ単位で区切っておくと、**その期間だけ差し替えられる**。

```
out/orders/date=2024-01-14/part-0.parquet
out/orders/date=2024-01-15/part-0.parquet    ← ここだけ消して書き直せる
out/orders/date=2024-01-16/part-0.parquet
```

これがパーティショニングで、
「1つのディレクトリ = 1つの原子的な差し替え単位」という設計になる。
クエリ側も `WHERE date = '2024-01-15'` でディレクトリごと読み飛ばせる([05](05-columnar-and-parquet.md))。

## どの時刻で区切るか

「1日ぶん」の1日を、**どの列で切るか**。ここを間違えると数字が合わなくなる。

| 時刻 | 意味 | 特徴 |
| --- | --- | --- |
| **イベント時刻** | 実際に注文が起きた時刻 | 業務的に正しい。**遅れて届く** |
| **取り込み時刻** | こちらに届いた時刻 | 遅れない。**業務的に意味がない** |

```
1/15 23:58 に注文  →  ネットワーク遅延  →  1/16 00:03 に届く

イベント時刻で切る:  1/15 のパーティションに入る。だが 1/15 のバッチはもう終わっている
取り込み時刻で切る:  1/16 のパーティションに入る。1/15 の売上が 1/16 に計上される
```

**どちらにも問題がある。** 現実解は、

- **保存はイベント時刻で区切る**(業務的な正しさを優先)
- **遅れて届いた分で、過去のパーティションを作り直す**(バックフィル)
- **いつまで遅れを待つかを決める**(ウォーターマーク → [04](04-idempotency-and-replay.md))

「1/15のデータは1/16の朝には確定している」ではなく、
「**1/15のデータは1/18まで変わりうる**」を前提に組む。

## タイムゾーン

日次バッチの「1日」は、誰にとっての1日か。

- 保存は **UTC** で統一する。例外なく
- 区切りと表示のときだけ **JST** に変換する
- 列名に単位を書く。`created_at_utc` / `order_date_jst`

タイムゾーンが混在した列は、後から分離できない。
`2024-01-15 09:00` がUTCなのかJSTなのか、値を見ても分からないため。

これは[03](03-dirty-data.md)でいう「意味の汚れ」で、**発見が最も遅れる種類**の事故。

## 依存とオーケストレーション

層を分けると、実行順の依存が生まれる。

```
     取り込み(注文)  ──┐
                      ├─→  整形  ──→  集計  ──→  BI
     取り込み(顧客)  ──┘
```

これを回すのがオーケストレータ(Airflow / Dagster / Prefect)の仕事。
中心にある考え方はDAG(有向非巡回グラフ)で、
**「何を、何のあとに、どの単位で」** を宣言する。

`cron` で時刻をずらして並べるのは、依存を「たぶん終わってるだろう」で表現している状態。
上流が5分遅れた日に、下流が**古いデータで成功する**。

| | cronで時刻をずらす | DAGで依存を書く |
| --- | --- | --- |
| 上流が遅れたら | 下流が古いデータで**成功する** | 下流が待つ |
| 上流が失敗したら | 下流が**走ってしまう** | 下流が走らない |
| 過去分の再実行 | 手で順番に叩く | 期間を指定して一括 |

これは[07](07-orchestration.md)で扱う。

## 設計の順番

1. **層を決める**(生 / 整形 / 集計)
2. **区切りを決める**(日次? 時次? どの時刻列で?)
3. **1回の実行を、期間を引数に取る関数として書く**
4. **その期間の出力を、丸ごと差し替えられるようにする**
5. **依存をDAGで宣言する**

3と4ができていれば、たいていの障害は「その期間だけ流し直す」で復旧できる。
できていなければ、全件洗い替えか、手作業のSQLになる。
