# 04. 冪等性とリプレイ — 二度流しても壊れない

> 対応するクエスト: quest-03 idempotency(予定) / quest-04 incremental(予定)

## 前提: パイプラインは必ず二度流れる

- 途中で失敗して、リトライされる
- 上流のデータが間違っていて、流し直す
- 集計ロジックのバグが見つかって、過去分を作り直す
- 誰かが手で叩く
- オーケストレータのバグで二重起動する

「一度しか流さない」設計は、**運用開始1週間で破綻する**。

## 冪等性の定義

> **同じ入力に対して何度実行しても、結果が同じになる。**

数学の `f(f(x)) = f(x)` そのもの。データパイプラインでは、
「2回流した後の状態」が「1回流した後の状態」と一致することを指す。

冪等でない典型は**追記**。

```sql
INSERT INTO daily_sales SELECT date, sum(amount) FROM orders WHERE date = '2024-01-15' GROUP BY 1;
```

2回流すと2行入る。合計を取る下流で**きれいに2倍**になる。
エラーは出ない。[01](01-what-is-data-engineering.md)でいう「黙る障害」。

## 冪等にする4つの型

### 型1: 全件洗い替え (full refresh)

```sql
BEGIN;
TRUNCATE daily_sales;
INSERT INTO daily_sales SELECT ...;   -- 全期間
COMMIT;
```

最も単純で、最も確実。**データが小さいうちはこれでよい。**

- 長所: 考えることが無い。過去の修正が自動で反映される
- 短所: データ量に比例して遅くなる。実行時間が窓に収まらなくなったら終わり

### 型2: パーティション単位の差し替え (delete-insert / insert-overwrite)

**実務で最もよく使う形。**

```sql
BEGIN;
DELETE FROM daily_sales WHERE date = '2024-01-15';
INSERT INTO daily_sales SELECT ... WHERE date = '2024-01-15';
COMMIT;
```

ファイルなら、ディレクトリごと差し替える。

```
out/daily_sales/date=2024-01-15/   ← 中身を消して書き直す
```

**必ずトランザクション、または原子的なリネームで囲む。**
消した直後に落ちると、その期間のデータが消えたまま残る。

ファイルシステムでの原子性は、一時ディレクトリに書いてからリネームで作る。

```
tmp/date=2024-01-15/  に全部書く
  ↓ 成功したら
out/date=2024-01-15/  を消して、tmp をリネーム
```

> [!NOTE]
> オブジェクトストレージ(S3など)には**ディレクトリのリネームが無い**。
> これがテーブルフォーマット(Iceberg / Delta Lake)が生まれた理由の一つで、
> あれらは「どのファイル群が今のテーブルか」をメタデータで管理して
> 原子的な差し替えを実現している([10](10-lakehouse.md))。

### 型3: MERGE / UPSERT

キー単位で「あれば更新、なければ挿入」。

```sql
MERGE INTO customers t
USING staged s ON t.customer_id = s.customer_id
WHEN MATCHED THEN UPDATE SET name = s.name, updated_at = s.updated_at
WHEN NOT MATCHED THEN INSERT (customer_id, name, updated_at) VALUES (...);
```

- 長所: 行単位の更新ができる。ディメンションテーブル向き
- 短所: **削除が反映されない**。ソースから消えた行が残り続ける

削除まで扱いたいなら、ソース側に論理削除フラグを出してもらうか、
定期的に全件洗い替えを挟む。

> [!WARNING]
> `USING` 側にキーの重複があると、多くのDBで
> `MERGE` は実行時エラーになる(あるいは非決定的な結果になる)。
> **MERGEの前に重複排除する**([03](03-dirty-data.md)の型7)。

### 型4: 追記 + 下流で最新だけ見る

追記しかしない(イミュータブル)。読む側が最新版を選ぶ。

```sql
SELECT * FROM (
  SELECT *, row_number() OVER (PARTITION BY order_id ORDER BY ingested_at DESC) rn
  FROM orders_log
) WHERE rn = 1
```

- 長所: 書き込みが単純で速い。**全履歴が残る**(監査、タイムトラベル)
- 短所: 読むたびにコストがかかる。放っておくと無限に太る

イベントソーシング的な考え方で、CDC([11](11-cdc.md))の受け口はこの形になることが多い。

## 冪等性を壊すもの

### `now()` / `today()`

```python
target_date = datetime.date.today()          # NG
```

昨日の分を流し直したいのに、今日の分が処理される。
**実行日と対象期間は別の概念**。対象期間は必ず外から渡す([02](02-pipeline-shapes.md))。

SQLの中の `now()` も同じ。

```sql
WHERE created_at >= now() - interval '1 day'   -- NG。流す時刻で結果が変わる
WHERE created_at >= :target_date               -- OK
```

### 自動採番の主キー

```sql
CREATE TABLE daily_sales (id serial PRIMARY KEY, date date, amount bigint);
```

流し直すたびに `id` が変わる。下流がこの `id` で参照していると全部壊れる。

集計結果の主キーは、**業務的な意味を持つ列の組**にする(`date` + `region` など)。
どうしても代理キーが要るなら、内容から決定的に導出する(ハッシュ)。

### 外部への副作用

```python
send_slack_notification(f"{len(df)} 件を処理しました")
```

パイプラインを10回流し直すと、通知が10回飛ぶ。
副作用は「変換」から分離し、オーケストレータ側に持たせる。

### 乱数とハッシュのシード

サンプリングや匿名化で乱数を使うなら、**シードを固定する**。
Pythonの `hash()` は実行ごとに変わる(`PYTHONHASHSEED`)ので、
永続化する値の導出に使ってはいけない。`hashlib` を使う。

## リプレイとバックフィル

### バックフィル = 過去の期間を流し直すこと

冪等な設計ができていれば、これはただのループになる。

```bash
for d in 2024-01-01 .. 2024-01-31; do
  python pipeline.py --date $d
done
```

冪等でなければ、手作業のDELETEとINSERTと祈りになる。
**バックフィルの容易さは、冪等性の設計品質そのもの。**

実務では並列度に注意する。全期間を一斉に流すと上流のDBを潰す。

### ウォーターマーク = どこまで処理したか

増分取り込みでは「前回どこまで読んだか」を持つ。

```
last_watermark = 2024-01-15 23:59:59
今回の対象:  created_at > last_watermark
```

これには**遅れて届くデータ**の問題がある。

```
1/15 23:58 のイベントが 1/16 00:03 に届く
  → 1/16 のバッチが動くとき、ウォーターマークは既に 1/16 00:00 を超えている
  → このイベントは永久に処理されない
```

対処は、ウォーターマークに**猶予(lateness)を持たせる**。

```
今回の対象:  created_at > last_watermark - 3 days
```

3日ぶん重複して読むことになるので、**書き込み側が冪等である必要がある**。
型2か型3を使う。ここで型「追記」を選んでいると3日ぶん二重計上する。

> **遅れて届くデータへの耐性は、冪等な書き込みの上にしか作れない。**

猶予を何日にするかは、実データを見て決める。
`ingested_at - event_time` の分布を取り、99パーセンタイルを見る。
**この分布を測らずに「たぶん1日」で決めると、必ず取りこぼす。**

## リトライ耐性

冪等性はリトライの前提条件でもある。

| 落ちる場所 | 冪等でない場合 | 冪等な場合 |
| --- | --- | --- |
| 書き込み前 | 影響なし | 影響なし |
| 書き込み途中 | **中途半端なデータが残る** | 差し替え単位ごと無効。再実行で復旧 |
| 書き込み後、記録前 | **二重に書かれる** | もう一度書いても同じ |

3行目が「exactly-once が難しい」と言われる本質。
「ちょうど1回書く」の保証は分散システムでは非常に高価だが、
**「何回書いても同じ」なら安く達成できる**。

> **exactly-once を目指すな。at-least-once + 冪等 を目指せ。**

これはストリーミング([12](12-streaming.md))でも同じ結論になる。

## チェックリスト

- [ ] 対象期間を引数で受け取っているか。`today()` を使っていないか
- [ ] 書き込みが「差し替え」になっているか。追記になっていないか
- [ ] 差し替えがトランザクション、または原子的リネームで囲まれているか
- [ ] 主キーが決定的か。`serial` を使っていないか
- [ ] 同じ期間を2回流して、結果が一致することを**テストしたか**
- [ ] ウォーターマークに猶予があるか。その日数の根拠があるか
- [ ] 通知やAPI呼び出しなどの副作用が、変換から分離されているか

5番目が肝心。冪等性は主張ではなく**検証できる性質**なので、
「2回流して差分が無いこと」をテストに入れる。
