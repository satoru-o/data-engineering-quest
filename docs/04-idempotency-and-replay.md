# 04. 冪等性とリプレイ — 二度流しても壊れない

> 対応するクエスト: quest-03 idempotency(予定) / quest-04 incremental(予定)

## 前提: パイプラインは何度も流れる

- 途中で失敗して、リトライされる
- 上流のデータが間違っていて、流し直す
- 集計ロジックのバグが見つかって、過去分を作り直す
- 誰かが手で叩く
- オーケストレータの不具合で二重に起動する

どれも運用ではよく起きることです。
そのため「一度しか流さない」前提の設計は、早い段階で行き詰まります。

## 冪等性の定義

> **同じ入力に対して何度実行しても、結果が同じになること。**

数学の `f(f(x)) = f(x)` と同じ考え方です。データパイプラインでは、
「2回流した後の状態」が「1回流した後の状態」と一致することを指します。

冪等でなくなりやすいのは**追記**です。

```sql
INSERT INTO daily_sales SELECT date, sum(amount) FROM orders WHERE date = '2024-01-15' GROUP BY 1;
```

2回流すと2行入ります。合計を取る下流では、金額が2倍になります。
このときエラーは出ません。[01](01-what-is-data-engineering.md) でいう「黙る障害」にあたります。

## 冪等にする4つの型

### 型1: 全件洗い替え (full refresh)

```sql
BEGIN;
TRUNCATE daily_sales;
INSERT INTO daily_sales SELECT ...;   -- 全期間
COMMIT;
```

いちばん単純で、確実な方法です。**データが小さいうちは、これで十分です。**

- 長所: 考えることが少ない。過去の修正が自動で反映される
- 短所: データ量に比例して遅くなる。実行時間が窓に収まらなくなったら次の型へ移る

### 型2: パーティション単位の差し替え (delete-insert / insert-overwrite)

**実務でよく使われる形です。**

```sql
BEGIN;
DELETE FROM daily_sales WHERE date = '2024-01-15';
INSERT INTO daily_sales SELECT ... WHERE date = '2024-01-15';
COMMIT;
```

ファイルなら、ディレクトリごと差し替えます。

```
out/daily_sales/date=2024-01-15/   ← 中身を消して書き直す
```

このとき、**トランザクションか、原子的なリネームで囲んでおきます。**
消した直後に失敗すると、その期間のデータが消えたままになるためです。

ファイルシステムでの原子性は、一時ディレクトリに書いてからリネームすると作れます。

```
tmp/date=2024-01-15/  に全部書く
  ↓ 成功したら
out/date=2024-01-15/  を消して、tmp をリネーム
```

> [!NOTE]
> オブジェクトストレージ(S3など)には**ディレクトリのリネームがありません**。
> これがテーブルフォーマット(Iceberg / Delta Lake)が生まれた理由の一つで、
> 「どのファイル群が今のテーブルか」をメタデータで管理することで
> 原子的な差し替えを実現しています([10](10-lakehouse.md))。

### 型3: MERGE / UPSERT

キー単位で「あれば更新、なければ挿入」を行います。

```sql
MERGE INTO customers t
USING staged s ON t.customer_id = s.customer_id
WHEN MATCHED THEN UPDATE SET name = s.name, updated_at = s.updated_at
WHEN NOT MATCHED THEN INSERT (customer_id, name, updated_at) VALUES (...);
```

- 長所: 行単位で更新できる。ディメンションテーブルに向いている
- 短所: **削除が反映されない**。ソースから消えた行が残り続ける

削除まで扱いたい場合は、ソース側に論理削除フラグを出してもらうか、
定期的に全件洗い替えを挟みます。

> [!WARNING]
> `USING` 側にキーの重複があると、多くのデータベースで
> `MERGE` は実行時エラーになります(結果が一定しない場合もあります)。
> **MERGE の前に重複排除をしておいてください**([03](03-dirty-data.md) の型7)。

### 型4: 追記 + 下流で最新だけ見る

追記だけを行い(イミュータブル)、読む側が最新版を選ぶ形です。

```sql
SELECT * FROM (
  SELECT *, row_number() OVER (PARTITION BY order_id ORDER BY ingested_at DESC) rn
  FROM orders_log
) WHERE rn = 1
```

- 長所: 書き込みが単純で速い。**全履歴が残る**(監査、タイムトラベル)
- 短所: 読むたびに計算コストがかかる。放っておくとデータが増え続ける

イベントソーシングに近い考え方で、CDC([11](11-cdc.md))の受け口はこの形になることが多いです。

## 冪等性を壊すもの

### `now()` / `today()`

```python
target_date = datetime.date.today()
```

昨日の分を流し直したいのに、今日の分が処理されてしまいます。
**実行日と対象期間は別の概念**なので、対象期間は外から渡します([02](02-pipeline-shapes.md))。

SQL の中の `now()` も同じです。

```sql
WHERE created_at >= now() - interval '1 day'   -- 流す時刻で結果が変わる
WHERE created_at >= :target_date               -- 外から渡す
```

### 自動採番の主キー

```sql
CREATE TABLE daily_sales (id serial PRIMARY KEY, date date, amount bigint);
```

流し直すたびに `id` が変わります。下流がこの `id` で参照していると、対応が取れなくなります。

集計結果の主キーは、**業務的な意味を持つ列の組**にしておきます(`date` + `region` など)。
どうしても代理キーが必要なら、内容から決定的に導出します(ハッシュなど)。

### 外部への副作用

```python
send_slack_notification(f"{len(df)} 件を処理しました")
```

パイプラインを10回流し直すと、通知も10回飛びます。
副作用は「変換」から分けて、オーケストレータ側に持たせると扱いやすくなります。

### 乱数とハッシュのシード

サンプリングや匿名化で乱数を使うなら、**シードを固定します**。
Python の組み込み `hash()` は実行ごとに結果が変わる(`PYTHONHASHSEED`)ので、
保存する値の導出には `hashlib` を使ってください。

## リプレイとバックフィル

### バックフィル = 過去の期間を流し直すこと

冪等な設計ができていれば、これは単純なループになります。

```bash
for d in 2024-01-01 .. 2024-01-31; do
  python pipeline.py --date $d
done
```

冪等でない場合は、手作業の DELETE と INSERT を積み重ねることになります。
**バックフィルのやりやすさは、冪等性がどれだけ設計に入っているかで決まります。**

実務では並列度にも気を配ります。全期間を一斉に流すと、上流のデータベースに負荷がかかります。

### ウォーターマーク = どこまで処理したか

増分取り込みでは「前回どこまで読んだか」を持ちます。

```
last_watermark = 2024-01-15 23:59:59
今回の対象:  created_at > last_watermark
```

ここで**遅れて届くデータ**が問題になります。

```
1/15 23:58 のイベントが 1/16 00:03 に届く
  → 1/16 のバッチが動くとき、ウォーターマークは既に 1/16 00:00 を超えている
  → このイベントが処理されないまま残る
```

対処としては、ウォーターマークに**猶予(lateness)を持たせます**。

```
今回の対象:  created_at > last_watermark - 3 days
```

3日ぶんを重複して読むことになるので、**書き込み側が冪等である必要があります**。
型2か型3を使ってください。ここで追記の型を選んでいると、3日ぶんが二重に計上されます。

> 遅れて届くデータへの耐性は、冪等な書き込みの上に作られます。

猶予を何日にするかは、実データを見て決めます。
`ingested_at - event_time` の分布を取り、99パーセンタイルあたりを見ます。
分布を見ないまま「たぶん1日でよいだろう」と決めると、取りこぼしが出やすくなります。

## リトライ耐性

冪等性は、リトライを安全にするための前提でもあります。

| 落ちる場所 | 冪等でない場合 | 冪等な場合 |
| --- | --- | --- |
| 書き込み前 | 影響なし | 影響なし |
| 書き込み途中 | **中途半端なデータが残る** | 差し替え単位ごと無効。再実行で復旧 |
| 書き込み後、記録前 | **二重に書かれる** | もう一度書いても同じ |

3行目が「exactly-once(ちょうど1回)は難しい」と言われる理由です。
「ちょうど1回書く」ことの保証は分散システムでは高くつきますが、
**「何回書いても同じ」なら、比較的簡単に実現できます**。

そのため、exactly-once を目指すよりも
**at-least-once(最低1回)+ 冪等**の組み合わせを目指すのが現実的です。
これはストリーミング([12](12-streaming.md))でも同じ結論になります。

## チェックリスト

- [ ] 対象期間を引数で受け取っているか。`today()` を使っていないか
- [ ] 書き込みが「差し替え」になっているか。追記になっていないか
- [ ] 差し替えがトランザクション、または原子的リネームで囲まれているか
- [ ] 主キーが決定的か。`serial` を使っていないか
- [ ] 同じ期間を2回流して、結果が一致することを**テストしたか**
- [ ] ウォーターマークに猶予があるか。その日数の根拠があるか
- [ ] 通知やAPI呼び出しなどの副作用が、変換から分離されているか

5番目が要になります。冪等性は主張ではなく**検証できる性質**なので、
「2回流して差分が無いこと」をテストに入れておくと安心です。
