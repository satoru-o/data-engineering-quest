# 01. データエンジニアリングとは何をする仕事か

## 一行で言うと

**「使えるデータが、使いたい形で、使いたいときに、そこにある」状態を維持する仕事。**

分析でもモデリングでもない。分析する人がその前段で消耗しないようにするのが仕事の中身で、
成果物は「答え」ではなく「答えを出せる状態」になる。

## なぜ独立した職能になったのか

データを使う側の要求は、だいたいこの3つに分解できる。

| 要求 | 具体的には |
| --- | --- |
| **見つかる** | どこに何があるか分かる |
| **信用できる** | 数字が合っている。昨日と今日で意味が変わらない |
| **速い** | 待たされない |

1つのアプリのDBを1人が使っている間は、これは自然に満たされる。
壊れるのは**規模と関係者が増えたとき**で、増え方は3方向ある。

- **データ源が増える** — 表記も文字コードも粒度も揃っていないものが並ぶ
- **利用者が増える** — 同じ「売上」を各自が各自の定義で計算しはじめる
- **量が増える** — 「全部読んで集計」が終わらなくなる

どれも個々の分析者には解けない。**共通の層を誰かが持つ**しかない。
それがデータエンジニアリングという職能の存在理由になっている。

## 仕事の全体像

データは、ざっくりこの順に流れる。

```
  生成      →   取り込み   →   保存      →   変換      →   提供
  Generation    Ingestion      Storage       Transform     Serving
  アプリ         バッチ/CDC     オブジェクト   集計・結合    BI / ML
  ログ           ストリーム     DWH/レイク    モデリング    API
  外部API                                    品質チェック
```

この横棒の下を、全区間にわたって支えるものがある。

```
  ─────────────────────────────────────────────────────────
  オーケストレーション / データ品質 / メタデータ・リネージ
  セキュリティ / コスト / DataOps
```

**上の5段が「何をするか」、下の帯が「どう回し続けるか」。**
初心者は上ばかり見るが、実務で時間を食うのは圧倒的に下の帯のほう。
パイプラインは書くより**動かし続けるほうが難しい**。

## 「壊れる」の中身

パイプラインの障害には、性質のまったく違う2種類がある。

| | 止まる障害 | **黙る障害** |
| --- | --- | --- |
| 見え方 | ジョブが失敗する。アラートが鳴る | **成功して終わる** |
| 例 | 接続エラー、OOM、構文エラー | 文字化け、二重計上、暗黙の型変換、0件 |
| 気づく人 | 当日、エンジニア | 数週間後、経営会議 |
| 直すコスト | 小さい | **過去分の再計算が要る** |

エンジニアリングの重心は後者にある。
「例外が出る」は良い設計で、**「黙って間違った数字が出る」が最悪**。
このリポジトリのクエストが繰り返し扱うのはそこ。

## ETL と ELT

変換をどこでやるか、という話。

```
ETL:  抽出 → 【変換】 → 格納       変換は途中の処理系(Sparkなど)でやる
ELT:  抽出 → 格納 → 【変換】       まず生のまま入れて、DWHの中でSQLで変換する
```

歴史的にはETLが先。ストレージが高く、DWHの計算力が貧弱で、
**入れる前に減らす必要があった**から。

いまは順序が逆転している。オブジェクトストレージが安く、
DWH/クエリエンジンが速くなったので、**まず生のまま入れる**ほうが得になった。

| | ETL | ELT |
| --- | --- | --- |
| 生データ | 残らないことが多い | 残る |
| 仕様変更 | 取り込み直しが要る | **SQLを直して流し直すだけ** |
| 変換を書く人 | エンジニア | アナリストも書ける |
| コスト | 保存が安い | 計算が増える |

ELTの本質的な利点は「速い」ではなく、**やり直しが効く**こと。
「あの集計、実は定義が間違っていた」は必ず起きる。
そのとき生データが残っていれば直せるし、残っていなければ直せない。

> [!NOTE]
> ELTでも変換は消えない。**場所が移っただけ**で、
> 「生のまま入れる」は「汚いまま使う」ではない。
> 取り込みの直後に、最低限の正規化をした層を必ず作る。

## バッチとストリーム

| | バッチ | ストリーム |
| --- | --- | --- |
| 単位 | 期間で区切る(1日ぶん、1時間ぶん) | 1件ずつ |
| 遅延 | 分〜日 | 秒〜 |
| やり直し | **簡単。もう一度流す** | 難しい。オフセットの巻き戻し |
| 状態 | 各回が独立に書ける | 状態を持ち越す必要がある |
| 難しさ | 低い | 高い |

**迷ったらバッチ**。ストリームは、遅延要件が本当に厳しいときだけ。

「リアルタイムでほしい」と言われたら、必ず**それは何分までなら許されるのか**を聞く。
15分でよいなら15分ごとのバッチで済み、運用コストは一桁違う。

境界が曖昧に見えるのは、**マイクロバッチ**(短い間隔のバッチ)が両者の間を埋めているから。
Spark Structured Streaming の既定の動作もこれで、
「ストリーム処理」と呼ばれているものの多くは実体としてマイクロバッチ。

## この学習リポジトリの立ち位置

上の5段のうち、**取り込み・保存・変換**を手を動かして覚えるのが主眼。
下の帯からは**データ品質とオーケストレーション**を扱う。

BIツールの使い方、機械学習、クラウドの課金設計は範囲外。
