# 01. データエンジニアリングとは何をする仕事か

## 一行で言うと

**「使えるデータが、使いたい形で、使いたいときに、そこにある」状態を保つ仕事です。**

分析そのものやモデリングとは少し違います。分析する人が、その手前の準備で
時間を取られずに済むようにするのが仕事の中身で、
成果物は「答え」ではなく「答えを出せる状態」になります。

## なぜ独立した職能になったのか

データを使う側の要求は、だいたいこの3つに分けられます。

| 要求 | 具体的には |
| --- | --- |
| **見つかる** | どこに何があるか分かる |
| **信用できる** | 数字が合っている。昨日と今日で意味が変わらない |
| **速い** | 待たされない |

1つのアプリのデータベースを1人で使っている間は、この3つは自然に満たされます。
難しくなるのは**規模と関係者が増えたとき**で、増え方には3つの方向があります。

- **データ源が増える** — 表記も文字コードも粒度も揃っていないものが並びます
- **利用者が増える** — 同じ「売上」を、各自が各自の定義で計算しはじめます
- **量が増える** — 「全部読んで集計」が終わらなくなります

どれも、個々の分析者が自分の手元だけで解決するのは難しい問題です。
そこで**共通の層を誰かがまとめて持つ**ことになり、
それがデータエンジニアリングという職能の役割になっています。

## 仕事の全体像

データは、おおよそこの順に流れていきます。

```
  生成      →   取り込み   →   保存      →   変換      →   提供
  Generation    Ingestion      Storage       Transform     Serving
  アプリ         バッチ/CDC     オブジェクト   集計・結合    BI / ML
  ログ           ストリーム     DWH/レイク    モデリング    API
  外部API                                    品質チェック
```

そして、この流れの全区間を下から支えるものがあります。

```
  ─────────────────────────────────────────────────────────
  オーケストレーション / データ品質 / メタデータ・リネージ
  セキュリティ / コスト / DataOps
```

**上の5段が「何をするか」、下の帯が「どう回し続けるか」**です。

最初のうちは上の5段に目が行きますが、実務で時間がかかるのは下の帯のほうです。
パイプラインは、一度書くことよりも**動かし続けることのほうに手間がかかります**。
いまはピンと来なくても大丈夫です。手を動かしていくうちに実感できます。

## 「壊れる」の中身

パイプラインの障害には、性質の違う2種類があります。

| | 止まる障害 | **黙る障害** |
| --- | --- | --- |
| 見え方 | ジョブが失敗する。アラートが鳴る | **成功して終わる** |
| 例 | 接続エラー、メモリ不足、構文エラー | 文字化け、二重計上、暗黙の型変換、0件 |
| 気づく人 | 当日、エンジニア | 数週間後、経営会議 |
| 直すコスト | 小さい | **過去の分まで再計算が要る** |

このリポジトリで繰り返し扱うのは、後者のほうです。

「例外が出る」のは、むしろ良い設計です。
困るのは「黙って間違った数字が出る」ほうで、こちらは気づくきっかけがないためです。
エラーが出て止まってくれたら、その場で直せます。

## ETL と ELT

変換をどこでやるか、という話です。

```
ETL:  抽出 → 【変換】 → 格納       変換は途中の処理系(Sparkなど)でやる
ELT:  抽出 → 格納 → 【変換】       まず生のまま入れて、DWHの中でSQLで変換する
```

歴史的にはETLが先にありました。ストレージが高く、DWHの計算力も限られていたので、
**入れる前に減らしておく必要があった**ためです。

いまは事情が変わっています。オブジェクトストレージが安くなり、
DWHやクエリエンジンが速くなったので、**まず生のまま入れる**ほうが扱いやすくなりました。

| | ETL | ELT |
| --- | --- | --- |
| 生データ | 残らないことが多い | 残る |
| 仕様変更 | 取り込み直しが要る | **SQLを直して流し直すだけ** |
| 変換を書く人 | エンジニア | アナリストも書ける |
| コスト | 保存が安い | 計算が増える |

ELT の利点は「速いこと」よりも、**やり直しが効くこと**にあります。
「あの集計、実は定義が間違っていた」というのは、どこの現場でも起きます。
そのとき生データが残っていれば直せますし、残っていなければ取り直しから始めることになります。

> [!NOTE]
> ELT にしても変換の仕事が消えるわけではありません。**場所が移っただけ**です。
> 「生のまま入れる」は「汚いまま使う」という意味ではないので、
> 取り込みの直後に、最低限の正規化をした層を用意しておきます。

## バッチとストリーム

| | バッチ | ストリーム |
| --- | --- | --- |
| 単位 | 期間で区切る(1日ぶん、1時間ぶん) | 1件ずつ |
| 遅延 | 分〜日 | 秒〜 |
| やり直し | **簡単。もう一度流す** | 難しい。オフセットの巻き戻しが要る |
| 状態 | 各回が独立に書ける | 状態を持ち越す必要がある |
| 難しさ | 低い | 高い |

**迷ったらバッチで考えるのがおすすめです。**
ストリームは、遅延の要件が本当に厳しいときに選びます。

「リアルタイムでほしい」と言われたら、**それは何分までなら許されるのか**を聞いてみてください。
15分でよいなら15分ごとのバッチで足りますし、運用の手間はかなり変わります。

両者の境界が曖昧に見えるのは、**マイクロバッチ**(とても短い間隔のバッチ)が
間を埋めているためです。Spark Structured Streaming の既定の動作もこれで、
「ストリーム処理」と呼ばれているものの多くは、実体としてはマイクロバッチです。

## この学習リポジトリの立ち位置

上の5段のうち、**取り込み・保存・変換**を手を動かして覚えるのが主眼です。
下の帯からは**データ品質とオーケストレーション**を扱います。

BIツールの使い方、機械学習、クラウドの課金設計は範囲外にしています。
