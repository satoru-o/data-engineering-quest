# 03. データは汚い — 取り込み層が引き受けるもの

> 対応するクエスト: [quest-01: raw-ingest](../quest-01-raw-ingest/)

## 前提

**上流は直らない。**

これは諦めではなく、設計の出発点。データ源はたいてい他部署か他社のシステムで、
こちらの都合で仕様を変えてもらうことはできない。
交渉が実る場合もあるが、実るまでの数か月ぶんのデータは汚いまま流れてくる。

だから取り込み層(staging / bronze などと呼ばれる層)の役割はこう定義される。

> **下流が上流の事情を知らなくて済むようにする。**

下流の集計SQLに `CASE WHEN region IN ('east','East','EAST')` が現れたら、
それは取り込み層の敗北。

## 汚れのカタログ

### 1. 構造の汚れ — 読む前に落ちる

| 症状 | 原因 |
| --- | --- |
| `UnicodeDecodeError` | 文字コードがUTF-8ではない(CP932など) |
| 列がずれる | 値の中に区切り文字、クォートされていない改行 |
| 列が足りない/多い | ファイルによってスキーマが違う。列が追加された |
| ヘッダが無い / 2行ある | 人間向けの体裁で出力されている |

**これは幸運な部類。** 例外で止まるので、間違った数字が下流に出ない。

### 2. 表現の汚れ — 読めるが、意味が揃っていない

| 対象 | 現れ方 |
| --- | --- |
| 日付 | `2024-01-05` / `2024/01/05` / `2024年1月5日` / `01/05/24` / Excelの通し番号 `45296` |
| 数値 | `1200` / `1,200` / `¥1,200` / `1200円` / `1200.0` / `(1200)`(負数) |
| 全角半角 | `３` / `ＡＢＣ` / `￥` / `　`(全角空白) |
| 大小文字 | `east` / `East` / `EAST` |
| 空白 | 前後の空白、タブ、ノーブレークスペース ` ` |
| 欠損 | `NULL` / `null` / `N/A` / `-` / `不明` / `999` / 空文字 |
| 真偽値 | `1`/`0`, `Y`/`N`, `true`/`TRUE`/`True`, `有`/`無` |

**このカテゴリが一番危ない。** 例外が出ないので、
「金額が文字列のまま集計されて0になる」「日付が全部同じ日になる」が黙って起きる。

### 3. 意味の汚れ — 型は合っているが、内容が違う

| 症状 | 例 |
| --- | --- |
| 単位が混在 | 円と千円。ミリ秒と秒。cmとm |
| タイムゾーンが混在 | UTCとJSTが同じ列に |
| 粒度が違う | 1行=1注文のはずが、1行=1明細のファイルが混ざる |
| コード体系が変わった | 途中から地域コードの採番規則が変わった |
| 論理削除が反映されない | 取り消された注文が残り続ける |

**自動検出がほぼ不可能。** 気づくのは合計値を誰かが目視したとき。
これがあるので、取り込み層には必ず**件数と合計の記録**を残す。

### 4. 時間の汚れ — 重複と訂正

| 症状 | 対処 |
| --- | --- |
| 完全重複 | 再送。行単位の重複排除 |
| 主キー重複(訂正あり) | **どれが最新か**を決める列が要る |
| 遅れて届く | ウォーターマークの設計([04](04-idempotency-and-replay.md)) |
| 訂正で無効になる | 「後から届いた行が不正」→ **その注文ごと落とす**のか、前の行に戻すのか |

## 正規化の順番

**順番が結果を変える。** これは好みの問題ではない。

```
1. 読む            文字コードを正しく判定する
2. 全部文字列で持つ  推測させない
3. Unicode正規化    NFKC
4. 空白除去        strip
5. 欠損の判定       この時点で "N/A" などを null にする
6. 型変換          日付・数値へ
7. 重複排除        キーごとに1行を選ぶ
8. 除外            落とすべき行を落とす
9. 型を固める       スキーマに合わせる
```

### 2「全部文字列で持つ」がなぜ効くか

`pd.read_csv` も `duckdb` も、既定では**型を推測する**。推測は親切に見えて、
汚れを勝手に埋めてしまう。

```python
pd.read_csv(path)                                    # 推測される
pd.read_csv(path, dtype=str, keep_default_na=False)  # 全部文字列
```

推測に任せると、こうなる。

- `1,200` を含む列 → 全体が `object`(文字列)になる。合計すると文字列連結
- `NULL` という文字列 → 勝手に `NaN` に。逆に `-` は文字列のまま残る
- `order_id` が `00123` → 整数 `123` に。**先頭の0が消えて結合できなくなる**

最後のは実際によく事故る。**IDは常に文字列で扱う**。

DuckDBなら `all_varchar=true`。

```sql
SELECT * FROM read_csv('/data/*.csv', all_varchar=true);
```

### 3「NFKC」が日本語データで効く理由

全角の数字・記号・空白は、一つずつ `replace` すると必ず漏れる。
Unicode正規化のNFKCは、互換文字をまとめて標準形に潰す。

```python
import unicodedata
unicodedata.normalize("NFKC", "３個 ￥１，２００　")
# → '3個 ¥1,200 '
```

全角数字も全角記号も全角空白も、これ一発で寄る。
**日本語のデータを扱う取り込み層には、ほぼ無条件で入れてよい。**

> [!WARNING]
> NFKCは強い正規化なので、潰してほしくないものも潰す。
> `㈱` → `(株)`、`Ⅲ` → `III`、`①` → `1`。
> 顧客名や商品名で元の表記を保存する必要があるなら、
> **正規化前の値も別列で残す**か、対象列を限定する。

### 7「重複排除」で決めること

主キーが重複したとき、**どれを採用するかを決める列が要る**。

| 使える列 | 注意 |
| --- | --- |
| `ingested_at`(取り込み時刻) | 取り込み側で付けられる。**一意にしておくこと** |
| `updated_at`(上流の更新時刻) | 上流の時計を信用することになる |
| ファイルの到着順 | 並列で読むと壊れる |

同着があると結果が非決定的になり、**流すたびに数字が変わる**という最悪の状態になる。
同着が起こりうるなら、第2キー(`order_id` など)まで含めて全順序を作る。

### 7と8の順番

これが取り込み設計で一番間違えやすいところ。

```
訂正で無効になった注文:
  ORD-001  ingested_at=02:00  quantity=5     ← 正常
  ORD-001  ingested_at=03:00  quantity=(空)  ← 訂正。無効になった

除外 → 重複排除 の順:  02:00の行が生き残る  →  注文は有効なまま。仕様違反
重複排除 → 除外 の順:  03:00の行が選ばれる  →  除外される。正しい
```

「不正な行はさっさと捨てたい」という直感が裏目に出る。
**選んでから、捨てる。**

## pandasの落とし穴

### `GroupBy.last()` は「最後の行」ではない

```python
df.sort_values("ingested_at").groupby("order_id").last()
```

これは**列ごとに最後の非null値**を返す。行を1本選んでいるわけではない。
最新行の `amount` が欠損なら、古い行の `amount` がこっそり混ざった
**どの行にも存在しないキメラ**ができあがる。

行を選ぶならこう。

```python
df.sort_values("ingested_at").drop_duplicates(subset="order_id", keep="last")
```

SQLなら意図が明示的に書ける。

```sql
SELECT * FROM (
  SELECT *, row_number() OVER (PARTITION BY order_id ORDER BY ingested_at DESC) rn
  FROM raw
) WHERE rn = 1
```

### `errors="ignore"` は例外を消すだけ

```python
open(path, encoding="utf-8", errors="ignore")   # やってはいけない
```

読めないバイトを黙って捨てる。例外は消え、顧客名が壊れたデータが下流に流れる。
**構造の汚れ(気づける)を、意味の汚れ(気づけない)に変換している。**

正しい文字コードで読み直すか、判定できないなら止める。

### `NaN` は3種類ある

`None` / `float('nan')` / `pd.NaT` が混在する。
`nan != nan` なので `==` での比較が効かない。判定は `isna()` を使う。

## 契約で守る

正規化を頑張っても漏れる。最後に**スキーマで殴る**。

```python
schema = pa.schema([
    ("order_id",   pa.string()),
    ("order_date", pa.date32()),
    ("quantity",   pa.int32()),
])
pa.Table.from_pandas(df, schema=schema)   # 合わなければ例外
```

出力の直前でスキーマを強制すると、
**取りこぼした汚れが「黙る障害」ではなく「止まる障害」になる**。
これがデータ契約(data contract)の最小形で、
本格的にやるなら Great Expectations / dbt test / Pandera へ進む([06](06-data-quality.md))。

## 実務のチェックリスト

- [ ] 文字コードをファイルごとに判定しているか。決め打ちしていないか
- [ ] 列を**名前**で取っているか。位置で取っていないか
- [ ] IDを文字列で扱っているか
- [ ] 生データをそのまま保存しているか(壊したら戻せない)
- [ ] 取り込みごとに**件数と主要な合計値**を記録しているか
- [ ] 重複排除のキーに全順序があるか(同着が無いか)
- [ ] 落とした行を数えているか。**黙って捨てていないか**
- [ ] 出力にスキーマを強制しているか

最後から2番目が抜けがち。「除外」は正しい処理だが、
**除外率が突然10%に跳ねたら上流で何かが起きている**。数えていないと気づけない。
