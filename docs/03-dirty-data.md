# 03. データは汚い — 取り込み層が引き受けるもの

> 対応するクエスト: [quest-01: raw-ingest](../quest-01-raw-ingest/)
> 対応するチュートリアル: [tutorial-01: POS売上パイプライン](../tutorial-01-pos-pipeline/)

## 前提

**上流のデータは、こちらの都合では変えられないことが多いです。**

これは諦めというより、設計の出発点です。データ源はたいてい他部署や他社のシステムなので、
仕様を変えてもらうには時間がかかります。
交渉がうまくいく場合もありますが、そのあいだのデータは今の形のまま流れてきます。

そこで、取り込み層(staging / bronze などと呼ばれる層)の役割はこう考えます。

> **下流が上流の事情を知らなくて済むようにする。**

下流の集計SQLに `CASE WHEN region IN ('east','East','EAST')` のような式が現れたら、
それは取り込み層で吸収しきれていないサインです。
そういうときは、下流を直すのではなく取り込み層に戻って直します。

## 汚れのカタログ

### 1. 構造の汚れ — 読む前に落ちる

| 症状 | 原因 |
| --- | --- |
| `UnicodeDecodeError` | 文字コードがUTF-8ではない(CP932など) |
| 列がずれる | 値の中に区切り文字がある。クォートされていない改行 |
| 列が足りない/多い | ファイルによってスキーマが違う。列が追加された |
| ヘッダが無い / 2行ある | 人間が読む用の体裁で出力されている |

**この種類は、まだ扱いやすいほうです。** 例外で止まってくれるので、
間違った数字が下流に出ていくことはありません。

### 2. 表現の汚れ — 読めるが、意味が揃っていない

| 対象 | 現れ方 |
| --- | --- |
| 日付 | `2024-01-05` / `2024/01/05` / `2024年1月5日` / `01/05/24` / Excelの通し番号 `45296` |
| 数値 | `1200` / `1,200` / `¥1,200` / `1200円` / `1200.0` / `(1200)`(負数) |
| 全角半角 | `３` / `ＡＢＣ` / `￥` / `　`(全角空白) |
| 大小文字 | `east` / `East` / `EAST` |
| 空白 | 前後の空白、タブ、ノーブレークスペース ` ` |
| 欠損 | `NULL` / `null` / `N/A` / `-` / `不明` / `999` / 空文字 |
| 真偽値 | `1`/`0`, `Y`/`N`, `true`/`TRUE`/`True`, `有`/`無` |

**注意が要るのはこの種類です。** 例外が出ないので、
「金額が文字列のまま集計されて0になる」「日付が全部同じ日になる」といったことが
気づかないうちに起こります。

### 3. 意味の汚れ — 型は合っているが、内容が違う

| 症状 | 例 |
| --- | --- |
| 単位が混在 | 円と千円。ミリ秒と秒。cmとm |
| タイムゾーンが混在 | UTCとJSTが同じ列に入っている |
| 粒度が違う | 1行=1注文のはずが、1行=1明細のファイルが混ざる |
| コード体系が変わった | 途中から地域コードの採番規則が変わった |
| 論理削除が反映されない | 取り消された注文が残り続けている |

**この種類は、機械的に見つけるのが難しい**部類です。
気づくのは、合計値を誰かが見て違和感を持ったときになりがちです。
そのため取り込み層では、**件数と合計を毎回記録しておく**と早く気づけます。

### 4. 時間の汚れ — 重複と訂正

| 症状 | 対処 |
| --- | --- |
| 完全重複 | 再送によるもの。行単位で重複排除する |
| 主キー重複(訂正あり) | **どれが最新か**を決める列が要る |
| 遅れて届く | ウォーターマークの設計([04](04-idempotency-and-replay.md)) |
| 訂正で無効になる | 「後から届いた行が不正」→ その注文ごと落とすのか、前の行に戻すのかを決める |

## 正規化の順番

**順番によって結果が変わります。** 好みではなく、意味のある順序です。

```
1. 読む            文字コードを正しく判定する
2. 全部文字列で持つ  推測させない
3. Unicode正規化    NFKC
4. 空白除去        strip
5. 欠損の判定       この時点で "N/A" などを null にする
6. 型変換          日付・数値へ
7. 重複排除        キーごとに1行を選ぶ
8. 除外            落とすべき行を落とす
9. 型を固める       スキーマに合わせる
```

### 2「全部文字列で持つ」がなぜ効くか

`pd.read_csv` も `duckdb` も、既定では**型を推測します**。
推測は便利な機能ですが、汚れたデータでは意図しない解釈をされることがあります。

```python
pd.read_csv(path)                                    # 推測される
pd.read_csv(path, dtype=str, keep_default_na=False)  # 全部文字列
```

推測に任せると、たとえばこうなります。

- `1,200` を含む列 → 全体が `object`(文字列)になり、合計すると文字列連結になる
- `NULL` という文字列 → `NaN` になる。一方 `-` は文字列のまま残る
- `order_id` が `00123` → 整数 `123` になり、**先頭の0が消えて結合できなくなる**

最後の例はよく起こります。**IDは文字列で扱う**と覚えておくと安全です。

DuckDB なら `all_varchar=true` で同じことができます。

```sql
SELECT * FROM read_csv('/data/*.csv', all_varchar=true);
```

### 3「NFKC」が日本語データで効く理由

全角の数字・記号・空白を1つずつ `replace` していくと、どうしても漏れが出ます。
Unicode正規化の NFKC を使うと、互換文字をまとめて標準の形に寄せられます。

```python
import unicodedata
unicodedata.normalize("NFKC", "３個 ￥１，２００　")
# → '3個 ¥1,200 '
```

全角数字も全角記号も全角空白も、これで揃います。
**日本語のデータを扱う取り込み層では、たいていの場合に役立ちます。**

> [!WARNING]
> NFKC は変換の範囲が広いので、そのまま残したい表記まで変えてしまうことがあります。
> `㈱` → `(株)`、`Ⅲ` → `III`、`①` → `1` などです。
> 顧客名や商品名で元の表記を残す必要がある場合は、
> **正規化前の値も別の列に持っておく**か、適用する列を限定してください。

### 7「重複排除」で決めること

主キーが重複したとき、**どれを採用するかを決める列**が必要になります。

| 使える列 | 注意点 |
| --- | --- |
| `ingested_at`(取り込み時刻) | 取り込み側で付けられる。一意になるようにしておく |
| `updated_at`(上流の更新時刻) | 上流の時計を信用することになる |
| ファイルの到着順 | 並列で読むと順序が変わる |

同着があると、どちらが選ばれるかが決まりません。すると
**流すたびに数字が変わる**ことになり、原因を追いにくくなります。
同着が起こりうるなら、第2キー(`order_id` など)まで含めて順序が一つに決まるようにします。

### 7と8の順番

ここは間違えやすいところなので、例を見てみます。

```
訂正で無効になった注文:
  ORD-001  ingested_at=02:00  quantity=5     ← 正常
  ORD-001  ingested_at=03:00  quantity=(空)  ← 訂正。無効になった

除外 → 重複排除 の順:  02:00の行が生き残る  →  注文が有効なまま残ってしまう
重複排除 → 除外 の順:  03:00の行が選ばれる  →  除外される。こちらが期待どおり
```

「不正な行は先に捨てておきたい」と考えたくなりますが、
先に捨てると、無効になったはずの古い行が残ってしまいます。

**選んでから、捨てる。** この順番だけ覚えておけば大丈夫です。

## pandasで気をつけるところ

### `GroupBy.last()` は「最後の行」ではない

```python
df.sort_values("ingested_at").groupby("order_id").last()
```

これは**列ごとに最後の非null値**を返すもので、行を1本選んでいるわけではありません。
最新行の `amount` が欠損していると、1つ前の行の `amount` が混ざり、
**どの行にも存在しない値の組み合わせ**ができあがります。

行を選びたいときは、こちらを使います。

```python
df.sort_values("ingested_at").drop_duplicates(subset="order_id", keep="last")
```

SQL なら、意図をそのまま書けます。

```sql
SELECT * FROM (
  SELECT *, row_number() OVER (PARTITION BY order_id ORDER BY ingested_at DESC) rn
  FROM raw
) WHERE rn = 1
```

### `errors="ignore"` は例外を消すだけ

```python
open(path, encoding="utf-8", errors="ignore")
```

これは読めないバイトを黙って捨てる指定です。例外は出なくなりますが、
顧客名などが壊れたまま下流に流れていきます。

**気づける汚れ(構造の汚れ)を、気づきにくい汚れ(意味の汚れ)に変えてしまう**ので、
正しい文字コードで読み直すか、判定できないなら止めるほうが安全です。

### `NaN` は3種類ある

`None` / `float('nan')` / `pd.NaT` が混在します。
`nan != nan` なので `==` での比較は使えません。判定には `isna()` を使います。

## 契約で守る

正規化を丁寧にやっても、漏れは出ます。最後に**スキーマで確認する**と安心です。

```python
schema = pa.schema([
    ("order_id",   pa.string()),
    ("order_date", pa.date32()),
    ("quantity",   pa.int32()),
])
pa.Table.from_pandas(df, schema=schema)   # 合わなければ例外
```

出力の直前でスキーマを強制すると、
**取りこぼした汚れが「黙る障害」ではなく「止まる障害」になります**。
これがデータ契約(data contract)のいちばん小さな形です。
本格的にやるなら Great Expectations / dbt test / Pandera といった道具があります([06](06-data-quality.md))。

## 実務のチェックリスト

- [ ] 文字コードをファイルごとに判定しているか。決め打ちしていないか
- [ ] 列を**名前**で取っているか。位置で取っていないか
- [ ] IDを文字列で扱っているか
- [ ] 生データをそのまま保存しているか(壊すと戻せない)
- [ ] 取り込みごとに**件数と主要な合計値**を記録しているか
- [ ] 重複排除のキーで、順序が一つに決まるか(同着が無いか)
- [ ] 落とした行を数えているか。黙って捨てていないか
- [ ] 出力にスキーマを強制しているか

最後から2番目は忘れやすいところです。「除外」は必要な処理ですが、
**除外率が急に10%に上がったときは、上流で何かが変わっています**。
数えていれば、その変化に気づけます。
