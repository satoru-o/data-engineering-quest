# data-engineering-quest

データエンジニアリングを、基礎論の読み物と手を動かす実習の往復で身につける自習用リポジトリです。
[linux-quests](../linux-quests) の姉妹版になります。

> [!NOTE]
> 個人の自習用リポジトリです。閲覧は自由ですが、Pull RequestやIssueでの提案・報告は受け付けていません。

## 構成

```
docs/            基礎論。概念だけの読み物。実習から参照される
drills/          部品の練習。SQLとpandasの「知らないと気づかずに間違う」ところを確認する
tutorial-NN-*/   通しの実習。1本のパイプラインを最後まで一緒に作る
quest-NN-*/      腕試し。仕様だけ渡されて自力で作る
archive/         試したが採らなかったもの。経緯だけ残してある
```

`docs/` 以外は docker compose でディレクトリ内が完結します。

## 学習の階段

4段あります。下に行くほど**渡されるものが減り、自分で書く割合が増えます**。

| | やること | 答え | 詰まったとき |
| --- | --- | --- | --- |
| `docs/` | 読む | — | — |
| `drills/` | 部品を1つずつ試す | **各問に付いています** | 答えを開いて写す |
| `tutorial-NN-*/` | 上から実行して1本作り切る | **各問に付いています** | 答えを開いて写す |
| `quest-NN-*/` | 仕様から自力で実装する | ありません | READMEのヒントを順に開く |

**解けなくて止まってしまう、という状態を作らないための階段です。**
いきなり `quest` から始めると手がかりが少なく、`drills` だけだと部品の知識にとどまります。
その間を `tutorial` がつないでいます。

```
docs/01,03 を読む
   ↓
drills          pandas と SQL の書き方に慣れる
   ↓
tutorial-01     汚れたPOSログを日次サマリにするまでを、一緒に作る
   ↓
quest-01        同じ領域を、今度は仕様書だけで自力実装する
```

途中でつらくなったら、ひとつ上の段に戻ってかまいません。

## 設計原則

形式によって原則が違います。ここを混ぜないようにしています。

### 教材(drills / tutorial)

- **答えは必ず付けます。** `<details>` に隠して、すぐ下に置いてあります。写して動かすだけでも進められます
- **判定は `assert` です。** 通れば `OK` と出ます。採点も提出もありません
- **データは静的で、毎回同じです。** 手で数えて確かめられる大きさに抑えています
- **練習は軽く、こまめに。** 「列を1つ変えるだけ」くらいのものを、各節に1問ずつ置いています

### クエスト

linux-quests の原則を引き継いだうえで、「作る」形式のために2つ足しています。

- **FLAGはランダムな文字列です。** 読める単語にはしていません
- **FLAGはどのファイルにも平文では存在しません。** 見張り役のプロセスが起動時にメモリ上で生成します
- **正規の手順を踏むとFLAGが手に入ります。** 出力が仕様を満たしている**間だけ**現れるので、1回通しただけでは残らず、壊れると消えます
- **前提となるセットアップは`setup.sh`で自動化しています。**
- **「あるべき姿」は仕様書として渡します。** 診断や実装は仕様との差分を取る作業なので、仕様が無いと進められません。ただしクエストのREADMEには書かず、`spec/` に業務文書の形で置いています
- **(追加) データは毎回作り直されます。** 正解の行数も合計値も実行のたびに変わるので、前回の答えをそのまま使うことはできません
- **(追加) 判定は段階的に返します。** どのチェックが通らなかったかが `out/report.txt` に出ます。作る形式では、途中経過が分からないと進めないためです
- **(追加) 自分の答えはgit管理外です。** 次の節で説明します

## 自分の答えはコミットされない

手を動かす形式では、やったあと `work/` に自分のコードが残ります。
これがうっかりコミットされないよう、
**ルートの[.gitignore](.gitignore)で `work/` を丸ごと除外**してあります。

```
drills/           notebooks/   配布用。gitで管理する
tutorial-NN-*/    work/        自分のコード。git管理外。ここに書く
quest-NN-*/       skeleton/    雛形。gitで管理する
                  work/        自分のコード。git管理外。ここに書く
```

配る側のスクリプト(`start.sh` / `setup.sh`)は、**既にあるファイルを上書きしません**。
何度実行しても、書きかけのものが消えることはありません。

- ブランチを切る必要はありません。`git status` に出てこないので、事故になりません
- 雛形からやり直すとき: `./start.sh --reset`、または `cp skeleton/ingest.py work/ingest.py`
- どうしても残したい答えがあれば `git add -f quest-01-raw-ingest/work/ingest.py`

## 遊び方

```bash
cd drills && ./start.sh      # http://localhost:8888/lab
```

### チュートリアル(通しで作る)

```bash
cd tutorial-01-pos-pipeline && ./start.sh    # http://localhost:8889/lab
```

`work/01-ingest.ipynb` を開いて、上から順に実行していきます。

### クエスト(腕試し)

```bash
cd quest-01-raw-ingest
cat README.md          # ミッション確認
./setup.sh             # 環境と生データを用意する
cat spec/orders.md     # 仕様を読む
# あとは実装する

./verify.sh --status   # 判定を見る
./verify.sh 'FLAG{...}'
./teardown.sh
```

ヒントは各READMEの中に順を追って置いてあります。
まずヒント無しで少し粘ってみて、行き詰まったら開いてください。

## 依存関係

**バージョンはリポジトリルートの [pyproject.toml](pyproject.toml) と [uv.lock](uv.lock) だけで決まります。**
Dockerfile には教材のバージョンを書きません。

以前は `pip install pandas==2.2.3 ...` を3つの Dockerfile に直書きしていました。
これだと直接使うパッケージしか固定できず、その先の依存は入れ直すたびに変わります。
ドリルは `groupby().last()` の罠のように**バージョンで変わる挙動そのもの**を教材にしているので、
そこがずれると問題が成立しなくなります。ロックファイルはそれを防ぐためのものです。

教材ごとに要るものが少し違うので、[uv](https://docs.astral.sh/uv/) の workspace で分けてあります。

```
pyproject.toml                          メンバーの一覧だけ
uv.lock                                 全メンバー分をまとめて固定する
drills/pyproject.toml                   + jupyterlab
tutorial-01-pos-pipeline/pyproject.toml + jupyterlab, ipykernel
quest-01-raw-ingest/pyproject.toml      + ipython (ノートブックは使わない)
```

`ipykernel` は `jupyterlab` の依存として勝手に入るものですが、tutorial-01 では
**6系に留めるために明示しています。** ipykernel 7 はカーネルの内部構造が変わっており、
VS Code の Jupyter 拡張がカーネルを ready と判定できず、セルが `pending` のまま進みません
([microsoft/vscode-jupyter#17228](https://github.com/microsoft/vscode-jupyter/issues/17228))。
ブラウザの JupyterLab では起きないので、気付かずに踏むと原因が分かりにくい類のものです。
`uv.lock` は全メンバー共通なので、この固定は drills 側のイメージにも効きます。

```bash
uv sync --package dequest-drills   # ホストに環境を作る (触りたいときだけ)
uv add --package dequest-drills X  # 依存を足す
uv lock                            # ロックを取り直す
```

`uv.lock` を変えたら `docker compose build` でイメージに反映されます。
**ホスト側に uv を入れる必要はありません。**入っていなくても
`./start.sh` はコンテナの中で `uv sync` するので、そのまま動きます。

## 素材を直接読んでもFLAGが分からない理由

クエストだけの話です。ドリルとチュートリアルにFLAGはありません(答えは最初から付いています)。

| クエスト | FLAGの生成タイミング | 生成場所 |
| --- | --- | --- |
| 01 raw-ingest | 見張り役のプロセス起動時 | `checker` がメモリ上に持ち、**出力が仕様を満たしている間だけ** `out/flag.txt` に現れます |

生成器(`image/gen.py`)は読めるようにしてあります。読めば「どこがどう汚れているか」は分かりますが、
生データは実行のたびにランダムに作り直されるので、答えを覚えて使うことはできません。
そしてFLAGはそこには入っていません。
