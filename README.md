## 構成

```
docs/          基礎論。概念だけの読み物。クエストから参照される
quest-NN-*/    手を動かすクエスト。docker compose で完結する
```

## 設計原則

linux-quests の原則をそのまま引き継いだうえで、「作る」形式のために2つ足してある。

- **FLAGはランダムな文字列。** 読める単語にはしていない
- **FLAGはどのファイルにも平文で存在しない。** 見張り役のプロセスが起動時にメモリ上で生成する
- **正規の手順を踏まないとFLAGは手に入らない。** 出力が仕様を満たしている**間だけ**現れる。1回通しただけでは残らないし、壊れればすぐ消える
- **前提となるセットアップは`setup.sh`で自動化。**
- **「あるべき姿」は仕様書として与える。** 診断や実装は仕様との差分を取る作業なので、仕様が無いと解けない。ただしクエストのREADMEには書かず、`spec/` に業務文書の形で置く
- **(追加) データは毎回作り直される。** 正解の行数も合計値も実行のたびに変わる。前回の自分の答えも他人の答えも当てにならない
- **(追加) 判定は段階的に返す。** どのチェックが落ちたかが `out/report.txt` に出る。作る形式では、フィードバックループが無いと学習にならないため
- **(追加) 自分の答えはgit管理外。** 後述

## 自分の答えはコミットされない

作る形式なので、解いたあと `work/` に答えが残る。これがうっかりコミットされないよう、
**ルートの[.gitignore](.gitignore)で `quest-*/work/` を丸ごと除外**してある。

```
quest-NN-*/
  skeleton/     雛形。gitで管理する
  work/         自分のコード。git管理外。ここに書く
```

`setup.sh` が `skeleton/` の中身を `work/` に配る。
**既にあるファイルは絶対に上書きしない**ので、何度叩いても書きかけは消えない。

- ブランチを切る必要はない。`git status` に出てこないので、忘れて事故る余地が無い
- 除外はルートに1行だけ書いてあるので、**新しいクエストを足しても自動で効く**
- 雛形からやり直す: `cp skeleton/ingest.py work/ingest.py`
- どうしても残したい答えがあれば `git add -f quest-01-raw-ingest/work/ingest.py`

## 遊び方

```bash
cd quest-01-raw-ingest
cat README.md          # ミッション確認
./setup.sh             # 環境と生データを用意する
cat spec/orders.md     # 仕様を読む
# あとは実装する

./verify.sh --status   # 判定を見る
./verify.sh 'FLAG{...}'
./teardown.sh
```

ヒントは各READMEの中で段階的に公開してあるので、まずヒント無しで格闘してから読むのがおすすめ。

## 動作環境

- Docker / Docker Compose
- クエストのディレクトリで `docker compose` が完結する。ホスト側にPythonやDBを入れる必要はない

## 素材を直接読んでもFLAGが分からない理由

| クエスト | FLAGの生成タイミング | 生成場所 |
| --- | --- | --- |
| 01 raw-ingest | 見張り役のプロセス起動時 | `checker` がメモリ上に持ち、**出力が仕様を満たしている間だけ** `out/flag.txt` に現れる |

生成器(`image/gen.py`)は読めるようにしてある。読めば「どこがどう汚れているか」は分かるが、
生データは実行のたびにランダムに作り直されるので、答えを覚えることはできない。
そしてFLAGはそこには無い。
